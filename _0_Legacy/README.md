# Legacy and reference material

This tree contains inherited or pre-AdvCiv-SAS documentation and visual reference material. It is kept for source archaeology, comparison, troubleshooting, and LLM/code-agent review rather than as current AdvCiv-SAS documentation.

The top-level `Docs/` and `Images/` split intentionally mirrors [`_1_AdvCiv-SAS/`](/_1_AdvCiv-SAS/) where that makes comparisons easier.

## Docs

- `AdvCiv/` contains the inherited base-AdvCiv manual and related reference files.
- `BBAI/` contains Better BTS AI documentation, including its changelog and notes; the upstream code/history is available from [the Civ4 Better AI SourceForge project](https://sourceforge.net/p/civ4betterai/code/HEAD/tree/).
- `BUG/` contains inherited BUG documentation and local help files used by AdvCiv-SAS.
- `Civ4BUG_Python_API/` contains a local plain-text copy of the [Civ4 BUG Python API reference](https://civ4bug.sourceforge.net/PythonAPI/). The old SourceForge-derived folder/file names were shortened because their provenance is documented here and the extra repetition was not useful; the `_web` suffix in `all_classes_web.txt` marks content copied from the web rather than written for this repository.
- `K-Mod/` contains inherited K-Mod documentation.
- `Manifests/` lists what the base game and base AdvCiv ship, generated by our tools; see [Manifests](#manifests).
- `dev_logs/` contains the anonymized messages of Better BTS AI's SVN history and of K-Mod's and pre-SAS AdvCiv's Git history, used by the source-history tooling.

Imported material remains subject to its original rights and provenance; moving or renaming a local reference file does not make it AdvCiv-SAS-original work.

## Manifests

[`Manifests/`](/_0_Legacy/Docs/Manifests/) holds what the base game (vanilla, Warlords and BtS) and base AdvCiv ship, as lists of their files, text keys and names, never their content. Nothing here was inherited as is: AdvCiv-SAS's tools generate these files from those layers, as `dev_logs/` beside them is generated from their history.

- Why they exist: the base game's files are not in the repository, as we do not know whether republishing them is allowed, and base AdvCiv's text is only in old Git history. So CI and agents without a Civ4 install, such as ChatGPT with a light-source ZIP, read these instead; a grep for a key or a path answers whether a layer has it.
- What each holds:

| File | Written by | Holds |
| --- | --- | --- |
| [`building_art_lsystem_names_bts.tsv`](/_0_Legacy/Docs/Manifests/building_art_lsystem_names_bts.tsv) | [`building_art_lsystem_names.py`](/.github/workflows/README.md#buildxmlbuilding_art_lsystem_namespy) `--write` | the 24 names BtS's `CIV4CityLSystem.xml` uses |
| [`inherited_files.tsv`](/_0_Legacy/Docs/Manifests/inherited_files.tsv) | [`inherited_files.py`](/.github/workflows/README.md#buildsourceinherited_filespy) `--write` | every Python, XML, C++, `res` and `Config` file the base game and base AdvCiv ship, with its upstream file events; it feeds the [inherited files audit](/_1_AdvCiv-SAS/Docs/Source_Analysis/inherited_files_audit.md) |
| [`xml_sas_text_inherited_hashes.tsv`](/_0_Legacy/Docs/Manifests/xml_sas_text_inherited_hashes.tsv) | [`xml_sas_text_inherited.py`](/.github/workflows/README.md#buildxmlxml_sas_text_inheritedpy) `--write` | every inherited text key's source and English hash |
| [`xml_sas_text_inherited_names.tsv`](/_0_Legacy/Docs/Manifests/xml_sas_text_inherited_names.tsv) | the same | leader and civilization names in readable English |
| [`xml_text_undefined_inherited.tsv`](/_0_Legacy/Docs/Manifests/xml_text_undefined_inherited.tsv) | hand | base AdvCiv's own undefined text keys |

- The root README's [Inherited game text lists](/README.md#inherited-game-text-lists) explains what the text lists are for.
- Where and why here (the user, 2026-11-22):
  - They first sat beside the CI check that writes each, four in `.github/workflows/build/xml/` and one in `build/source/`, so finding them meant knowing every check; then together in `.github/workflows/data/`.
  - They serve more than CI, such as greps, the audit and external agents, and they describe inherited material, which is what `_0_Legacy` holds for archaeology, comparison and agent review. So they moved here, where the light-source ZIP already includes them.
  - They sit in `Docs/`, beside `dev_logs/`, because `_0_Legacy`'s top level mirrors `_1_AdvCiv-SAS` (`Docs`, `Images`), which a documentation check enforces; a first try at `_0_Legacy/Manifests/` failed it.
- Names considered and why they were not kept:
  - `data/`: could be anything, code, images or spreadsheets.
  - `Inherited_Lists/`: "inherited" repeats `_0_Legacy`, and we did not inherit lists; we wrote them about what we inherited.
  - `Manifests/` was kept: a manifest lists what a shipment contains without being the shipment, which is what these files are for each layer; the text check already called its hash list `MANIFEST`.
