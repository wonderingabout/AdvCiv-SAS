F001 - provisional KI#330 - supported-config master/vassal tech-contact power-bias exemption depends on an unrelated toggle
Status: NEW CURRENT SAS DEFECT ROOT, static evidence strong.
Evidence:
- AI_doDiplo initializes bVassalsOrMaster=false.
- That relation flag is set only inside SAS_AI_DO_DIPLO_TECH_TRADE_MASTER_FROM_TO_VASSAL_CONTACT_PERCENT_OPTIMIZE.
- The separately configurable SAS_AI_DO_DIPLO_POWER_TECH_TRADE_OPTIMIZE later skips its power modifier only when !bVassalsOrMaster is false.
- XML documentation for the power-bias option explicitly promises that the bias is not applied between members of a master-vassal(s) locus, and both options are independently enable/disable toggles.
Consequence:
- With preferential master/vassal contact disabled but power-based tech contact enabled, master/vassal or sibling-vassal contacts are incorrectly treated as ordinary rivals for the power modifier.
- Defaults mask the problem because both options are enabled.
Repair direction:
- Compute the master/vassal-locus relationship independently of the preferential-contact feature toggle; use that relation both for the contact bonus and for the power-bias exemption as appropriate.

F002 - provisional KI#331 - restrictive AI canScrap policy silently vetoes callers that assume CvUnit::scrap succeeded
Status: NEW CURRENT SAS CONTRACT DEFECT ROOT, cross-file; first proven from CvPlayerAI.cpp/CvUnit.cpp/CvTeam.cpp. CvUnitAI.cpp may broaden the caller set during file 002.
Root contract:
- CvUnit::scrap() returns void and silently returns when canScrap()==false.
- SAS canScrap now rejects most AI units, especially in recommended obsolete-only mode.
- Several inherited callers were written when canScrap was essentially only a fighting-state gate and therefore treat the call as if removal succeeded.
Confirmed consequence A - AI_doMilitary financial disband quota:
- Candidate collection uses AI_disbandValue and does not filter canScrap().
- The loop calls scrap(), calls doDelayedDeath(), then increments iDisbandCount regardless of whether scrap() actually set delayed death.
- A rejected candidate therefore consumes the per-turn disband quota and can prevent a later genuinely eligible obsolete unit from being considered.
- Current data makes this practical: a unit can already be cheapened by AI_disbandValue when its ObsoleteTech is known while canScrap still rejects it until the configured obsolete-era delay has elapsed.
Confirmed consequence B - AI_doTurnUnitsPost upgrade cleanup:
- The cleanup path calls scrap(), doDelayedDeath(), then unconditionally sets bKilled=true.
- If canScrap rejects the unit, doDelayedDeath is a no-op because scrap() never set delayed death, but the still-living unit is treated as killed and skips the later ordinary upgrade path.
Confirmed consequence C - capitulation nuke disarm:
- CvTeam::setVassal inherited advc.143b disarms a capitulating team by calling scrap() on every nuke.
- Recommended SAS obsolete-only AI scrapping rejects units with ObsoleteTech=NONE before later UnitAI exceptions are reached.
- Current UNIT_TACTICAL_NUKE and UNIT_ICBM both use UNITAI_ICBM and ObsoleteTech=NONE, so AI capitulation can retain nukes while a human capitulation still removes them because the restrictive gates are AI-only.
Repair direction:
- Routine optional disband/cleanup callers should prefilter canScrap and only consume quota / mark killed after successful removal (or the API could explicitly return success).
- Mandatory game-rule actions such as capitulation disarm should use a forced/internal removal path that is not blocked by routine AI preservation policy.
- Do not globally weaken canScrap merely to satisfy mandatory callers.

F002 / provisional KI#331 - CvUnitAI caller expansion
Historical interaction:
- The important ancestry is a cross-commit contract change, not a changed caller. Base AdvCiv's canScrap was broadly permissive outside a narrow fighting-state restriction, so inherited `scrap(); return;` code effectively meant "remove this unit and stop."
- Practical 5945 introduced the recommended restrictive AI obsolete-only policy. Practical 5979 simplified that policy further, but the old CvUnitAI callers remained.
- This explains why the earlier commit-oriented archaeology could inspect practical 5945 locally and miss the later current-tree consequence: the defect lives in the interaction between a new callee contract and unchanged old callers.
- Current no-site Settler cleanup provides a useful internal contrast: `AI_scrapSettlerWithNoValidSite` deliberately uses `scrapInternal()` after its own guards because generic Settler scrap policy would otherwise block the mandatory cleanup.

Confirmed CvUnitAI consequences:
1. Worker self-cleanup no longer removes Workers under the recommended mode.
   - Current Worker unit variants use `UNITAI_WORKER` and `ObsoleteTech=NONE`.
   - The AI_workerMove cleanup branch can call `scrap(); return;` after productive actions fail.
   - canScrap rejects these Workers, so the call can only burn that Worker's turn; it can also prevent later stranded/safety fallback in that update.

2. Excess land Explorers can enter a repeated no-progress branch.
   - In inherited AI_exploreMove, an excess explorer that has positive ATTACK value converts to UNITAI_ATTACK; otherwise it calls `scrap(); return;`.
   - Current Scout/Explorer-style units explicitly disallow UNITAI_ATTACK, so the conversion fallback can be unavailable.
   - Scout/Explorer/Airship can remain blocked until their configured obsolete delay permits scrapping.
   - The current Robotic Recon Drone is stronger proof: it is an EXPLORE land unit, disallows ATTACK, has a positive production cost, and has `ObsoleteTech=NONE`. Once it reaches the excess-explorer cleanup with no earlier action, generic scrap has no future eligibility escape, so the inherited branch can repeatedly no-op and return.

3. Escort Sea cleanup can be impossible exactly when invoked.
   - The inherited inferior-escort cleanup branch is reached while `getCargo()>0`.
   - If role conversion fails, it executes `scrap(); return;`.
   - Recommended canScrap rejects units carrying cargo, so this removal is categorically vetoed at that call site.

4. Explore Sea cleanup can repeatedly no-op for cargo-capable ships.
   - Inherited obsolete-role and excess-explorer cleanup branches call `scrap(); return;` after failed role-conversion paths.
   - Recommended policy rejects any cargo-capable unit even when empty because `cargoSpace()>0`.
   - A cargo-capable ship assigned EXPLORE_SEA can therefore satisfy the caller's cleanup decision while being categorically ineligible for generic scrap.

5. Barbarian trapped-ship cleanup can no-op.
   - Inherited AI_barbAttackSeaMove periodically detects a ship that cannot generate a useful path and calls `scrap(); return;`.
   - A cargo-capable Barbarian ship such as a Galley is categorically rejected by the new policy, turning the intended cleanup into a lost turn whenever that branch fires.

6. Settler transport retirement after unloading can never use generic scrap in recommended mode.
   - Inherited AI_settlerSeaMove can unload a now-inferior old transport and then call `scrap(); return;`.
   - The transport remains cargo-capable even when empty, so canScrap rejects it solely from cargo capacity.

7. Doomed-city capturable-unit scorched-earth cleanup can report success without removing the unit.
   - AI_retreatToCity's inherited evacuation fallback can probabilistically scrap a capturable unit in an evacuating own city and immediately `return true`.
   - Settlers/Workers are representative capturable units and have no ObsoleteTech.
   - Recommended AI canScrap therefore rejects the removal, yet the caller reports that it handled the unit; the civilian can remain in the doomed city and be captured.

Together with file 001's financial-disband quota, upgrade-cleanup, and capitulation-nuke cases, these are one contract root rather than separate KIs.

Suggested root repair remains:
- Optional cleanup: check `canScrap()` before treating the decision as completed, and only consume quotas / return success / mark killed after actual removal.
- Mandatory removal: use an explicit forced/context-specific internal removal path.
- If practical, make the public scrap operation return success so callers cannot silently confuse a veto with removal.
- Do not weaken global canScrap just to accommodate mandatory callers.

F004 - provisional KI#332 - leader hover callers pass literal civilization 1, so trait help can resolve another civilization's units/buildings
Status: NEW CURRENT SAS UI DEFECT ROOT, current-data proof strong.
Native contract:
- CvDLLWidgetData::parseLeaderHelp treats widget data2, when not -1, as a CivilizationTypes value and passes it to CvGameTextMgr::parseLeaderTraits.
- parseLeaderTraits forwards that civilization to parseTraits.
- parseTraits uses the supplied civilization to resolve trait fast-production UnitClass/BuildingClass entries to civilization-specific UnitTypes/BuildingTypes.
Current caller problem:
- Multiple Python WIDGET_PEDIA_JUMP_TO_LEADER callers pass literal data2=1 rather than the leader/player's civilization.
- Current civilization index 1 is CIVILIZATION_ARABIA, so those hovers resolve fast-production classes through Arabia regardless of the displayed leader.
- Current literal-1 callers occur in Scoreboard, Hall of Fame, Info Screen, Military Advisor, and several Sevopedia pages (Religion, Civic, Music).
Concrete current consequence:
- Shaka is Aggressive and Zulu; the Zulu Barracks-class replacement is the Ikhanda, and that class receives the Aggressive double-production trait effect.
- Arabia has no Barracks-class replacement. A literal-Arabia context therefore makes Shaka's trait hover identify ordinary Barracks instead of his actual Ikhanda for that fast-production line.
- Equivalent wrong-resolution opportunities exist for leaders whose civilization replaces other trait-affected classes.
Ancestry/accounting:
- The old commit-oriented archaeology had already source-proven this interaction while examining a later caller, but deliberately held it unnumbered pending firmer ancestry.
- Local Base AdvCiv 1.14 retains literal data2=1 in its inherited BUG Scoreboard and Sevopedia Index leader widgets under the same DLL contract. Practical 4732 is an early SAS-lineage occurrence, not the upstream birth of the convention. Current SAS inherited the Scoreboard case, independently replaced/corrected the Index path and later broadened the wrong convention across additional screens.
Repair direction:
- Callers that know the real player/civilization should pass that CivilizationTypes value.
- Generic leader contexts should reuse the same canonical leader-to-civilization selection used by the main Sevopedia Leader path.
- Do not blindly substitute -1: parseLeaderHelp currently uses data2==-1 to suppress leader hover help entirely.

F007 - KI#48 broadened; recommended KI#48.3 - AI_buildingValue effective-food signal double-counts unhealthy-food loss
Status: EXISTING BUILDING-VALUE FAMILY, current implementation defect confirmed.
Current code:
- AI_buildingValue obtains `iFoodDifference = foodDifference(false, true)` and `iHealthLevel = goodHealth() - badHealth() + ...`.
- It then computes `iEffectiveFood = max(0, iFoodDifference) - max(0, -iHealthLevel)` and only later forces zero for nonpositive happiness surplus.
Engine contract:
- CvCity::foodDifference(..., true) subtracts foodConsumption().

Ancestry / classification:
- This logic was introduced in practical 4950 as part of the broad KI#48 building-value prefilter family. Treating it as KI#48.3 is cleaner than assigning a new root number.
Repair direction:
- Do not subtract current unhealthiness again from foodDifference when bIgnoreFood=false / food consumption is included. Derive the intended growth signal from one authoritative net-food quantity, then apply the documented nonnegative clamp and happiness gate.

F015 - provisional KI#336 - dynamic map-heaviness fallback is computed before starting plots exist and therefore caches a neutral result
Status: NEW CURRENT SAS LIFECYCLE DEFECT ROOT; current default/support configuration reaches it.
Intended contract:
- SAS map-heaviness logic first classifies scripts listed explicitly as land-heavy or naval-heavy.
- Scripts intentionally absent from both lists fall back to a dynamic start-area classifier that counts major-civilization starting plots and classifies the map from those areas.

Current lifecycle failure:

Lineage:
- Practical 5032 introduced the script-name cache/call sites.
- Practical 5402 added the start-area dynamic fallback and persistence without moving the computation to a post-start phase.
Consequence:
- Supported scripts intentionally delegated to dynamic classification normally remain neutral instead of receiving their intended land/naval heuristic classification. AI logic consuming these flags can therefore miss its map-specific tuning.
Repair direction:
- Split script-name classification from the start-area-dependent phase, or explicitly recompute the dynamic fallback after starting plots have been assigned (including scenario/regeneration lifecycle considerations).
