Purpose
-------
Systematically review the historical AdvCiv and then K-Mod commit diffs for inherited bugs, regressions, suspicious behavior changes, and useful fixes that may still matter to AdvCiv-SAS. After completing those inherited-history sweeps, separately review AdvCiv-SAS branch history for surviving regressions and flaws in executable source code.

Primary sources
---------------
For an ordinary clone/Codex/IDE session, use the tracked greppable mirror:
  LLM_Helpers/commit_diffs/INDEX.txt
  LLM_Helpers/commit_diffs/PATH_HISTORY_INDEX.txt
  LLM_Helpers/commit_diffs/<segment>_<practical-count>_<short-sha>.diff

For a light-source handoff, `_SNAPSHOT_CONTEXT/commit_diffs/` is generated fresh from that snapshot's current Git ancestry with the same renderer/filtering policy. Current source and Git remain authoritative; the tracked mirror can lag HEAD until `python LLM_Helpers/sync_tracked_commit_diffs.py` is run.

Both this progress file and the tracked commit-diff mirror are kept in Git for future clone/LLM archaeology but export-ignored from player/release archives. The tracked mirror is excluded from its own generated historical patches to prevent recursive history-of-history growth.

Default sweep order
-------------------
1. AdvCivPreSAS newest -> oldest: practical 4343 down to 1250.
2. KMod newest -> oldest: practical 1249 down to 1.
3. When a finding points across a lineage boundary, trace that specific code farther immediately rather than waiting for the broad sweep to reach it.
4. Do not "fix" a merely suspicious historical choice without understanding current semantics and gameplay impact.
5. After the K-Mod sweep reaches practical 1, run a separate newest-to-oldest systematic sweep over AdvCiv-SAS branch history with the same evidence standard. The SAS phase has its own source-touching-SHA denominator and is not included in the completed 4,343 inherited-history total.
6. The SAS phase is intentionally source-focused: review runtime/game C++ (`*.cpp`, `*.h`) and Python (`*.py`) changes, including map scripts, while normally ignoring XML, Markdown/text documentation, art/binary assets and generated logs. Mixed commits are still reviewed for their executable-source hunks. Developer/CI helper Python can be audited separately but does not consume the primary runtime-source denominator.
7. SAS diffs can contain large CRLF/EOL-only churn, often alongside work produced through Codex/ChatGPT or other tooling. Do not skip such commits or discount them by authorship: treat practical number + SHA as identity and compare the before/after runtime source after normalizing line endings/whitespace noise where necessary. The goal is to reveal the substantive code hidden inside an enormous EOL patch, not to exclude the commit from review.
8. Freeze each SAS sweep inventory at its starting snapshot HEAD so bug-fix commits made during the sweep do not continuously move the denominator. Later commits can be reviewed as a small follow-up delta.

The pre-5851 ordered list intentionally produced opposite-side pairs after the stable y-sort. Passing through an unordered identity set destroys that same-y ordering while retaining all coordinate duplicates, so the endpoint pairing no longer has a correctness invariant.
  Concrete radius-4 row proof: the midpoint-circle generator emits the y=0 boundary sequence `(+4, -4, +4, -4)` as four distinct objects. With the old ordered list, the stable y-sort preserves those four equal-y entries and pairs `(+4,-4)` twice, drawing the full x=-4..+4 crater row. With the practical-5851 identity set, all four objects still survive but their iteration order is unspecified; an allowed equal-y order such as `(-4,-4,+4,+4)` pairs same-side endpoints and draws only degenerate x=-4 and x=+4 lines for that row. Other radii contain the same duplicate-endpoint structure. Thus crater shape can depend on unordered set iteration rather than the circle geometry.

No existing KI/tracker entry was found for this defect.

The active meteor rasterizer expects paired boundary points, and the filled-disk averaging callers introduced in the same upstream patch no longer rely on this boundary helper. F011 - KI#214: irrigation-chain constrained search could discard the only route that satisfied the plot limit - FIXED / VALIDATED
  Classification: AdvCiv-SAS path-search/state-model defect introduced by SAS practical 6076, SHA 2cc4ccaf5d, in `SAS_findWorkerIrrigationChainStep`.
  The search is Dijkstra-like and ranks nodes by `iCost`, but memoizes only one `aiBestCost[ePlot]` for each plot while also enforcing a separate maximum route length `iMaxPlots` (current default 12). Search cost is not a monotonic proxy for step count: each extra route step after the first costs 350, while overwriting a growth improvement costs 400 per growth level and a generic other improvement costs 2200. A longer detour through empty plots can therefore be cheaper than a shorter route through an existing improvement.
  Concrete counterexample under current defaults: a 2-step route to convergence plot X that crosses one generic improvement costs about 2200 + 350 = 2550; a 7-step empty detour to the same X costs 6 * 350 = 2100. The 7-step state wins `aiBestCost[X]`, so the valid 2-step state is discarded. If an irrigation source lies six additional steps beyond X, the retained cheap route needs 13 plots and is stopped by the 12-plot cap, while the discarded route would reach the source in only 8. The function can therefore return no route even though a legal route exists within `SAS_WORKER_AI_IRRIGATION_CHAIN_MAX_PLOTS`. Equal-cost routes with different step counts can produce the same structural problem because `>= aiBestCost` also discards the alternate state.
  Gameplay impact: the 6076 feature exists specifically to connect dry BFC Farms/food-pressure targets to available irrigation. In a layout where the cheapest detour exceeds the route cap but a more-expensive shorter chain fits, Workers can fail to discover the intended chain and leave a dry Farm unresolved despite an admissible route. The bug is geometric/state-dependent rather than guaranteed every game.
  Fixed in the current validated implementation batch by storing best cost for every bounded `(plot, steps)` state. This preserves least-cost routing subject to the hard step constraint without a heuristic special case. Save file 478 then completed a compiled-DLL Huge Pangaea autoplay through turn 497: Worker level-3 BBAI logging recorded 12,089 selected routes and exercised the exact depth-12 boundary in 344 failed searches without a route invariant failure, assertion or crash; SASGameRecord confirmed the normal Space Race victory endpoint and showed safe 32-bit process-memory headroom.

Recording rules
---------------
- Record clean progress as ranges rather than one line per harmless commit.
- For dense K-Mod/SAS archaeology, persist each completed checkpoint immediately instead of waiting for the whole segment or chat turn to finish. Use roughly 200 commits as a maximum checkpoint size and keep smaller live cursors while working when practical.
- Tooling/methodology note: this sweep was initially carried out primarily with ChatGPT in an interactive chat/tool environment (among other practical reasons, Codex usage availability was limited at the time). Interactive or otherwise non-persistent environments can sometimes interrupt a long review before a natural stopping point; more persistent coding-agent environments such as Codex or Claude Code may not share the same practical limitation.
- In an interactive/non-persistent environment, if a large commit or unresolved investigation is still in progress after roughly 20 minutes, save an OPEN checkpoint before continuing: preserve the last certified cursor, current candidate(s), partial findings/dispositions and exact next step. The ~20-minute interval is an empirical safety margin learned during this sweep, not a review-time limit or correctness rule; very large commits may span as many OPEN checkpoints as needed without advancing the certified cursor until the commit is genuinely closed.
- Never advance the certified cursor past an unfinished checkpoint merely because lower-numbered commits received exploratory spot checks.
- For every suspect/finding worth preserving, record segment, practical commit number, SHA, title, relevant file/function, classification and final disposition.
- Keep separate counts for open suspects, confirmed defects, actual fixes, inherited/pre-SAS bugs and SAS-specific regressions.
- A summary-only or partial archived diff is not automatically "clean"; if its title/path is relevant, inspect adjacent history/current source or obtain fuller source before closing it.
- Update Known Issues only for findings that deserve durable player/developer documentation; this tracker can hold weaker suspects and dead ends.
- Prefer accuracy over finding a bug in every commit. Most commits should be harmless.
