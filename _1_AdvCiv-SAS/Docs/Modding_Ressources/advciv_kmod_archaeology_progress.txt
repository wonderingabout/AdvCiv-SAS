Purpose
-------
Systematically review the historical AdvCiv and then K-Mod commit diffs for inherited bugs, regressions, suspicious behavior changes, and useful fixes that may still matter to AdvCiv-SAS.

Primary sources
---------------
For an ordinary clone/Codex/IDE session, use the tracked greppable mirror:
  LLM_Helpers/commit_diffs/INDEX.txt
  LLM_Helpers/commit_diffs/PATH_HISTORY_INDEX.txt
  LLM_Helpers/commit_diffs/<segment>_<practical-count>_<short-sha>.diff

For a light-source handoff, `_SNAPSHOT_CONTEXT/commit_diffs/` is generated fresh from that snapshot's current Git ancestry with the same renderer/filtering policy. Current source and Git remain authoritative; the tracked mirror can lag HEAD until `python LLM_Helpers/sync_tracked_commit_diffs.py` is run.

Both this progress file and the tracked commit-diff mirror are kept in Git for future clone/LLM archaeology but export-ignored from player/release archives. The tracked mirror is excluded from its own generated historical patches to prevent recursive history-of-history growth.

F004 - KI#207 UWAI random team-member selection index mismatch - FIXED
  Classification: inherited Base AdvCiv bug
  Discovery route: first previously-unfixed defect found by the systematic newest-to-oldest historical sweep.
  Introduced in AdvCivPreSAS practical 2945, SHA f016996eb6:
    "Let UWAI negotiate with a random team member"
  CvTeam::getRandomMemberAlive generated a 0-based random eligible-member index but compared it with MemberIter::nextIndex(), whose current-element-visible value starts at 1 and whose sequence includes ineligible AI members during human-only selection.
  For three all-AI members the old distribution was 2/3, 1/3, 0 rather than 1/3 each; for two members it was 100%, 0%. Mixed human/AI teams additionally compared a human-only random range against all-member iterator positions.
  The fix keeps the same one synchronized RNG roll and counts eligible members explicitly with a zero-based index.
  AdvCiv practical 3209 later modernized the RNG helper but preserved the faulty comparison. AgentIterator::nextIndex() already had the relevant semantics before practical 2945, so the defect exists from introduction rather than from a later iterator change.
  The sweep had earlier re-encountered the real ExtraFreeOutsideUnits bug at practical 3956, but SAS had already fixed/documented it as KI#92; KI#207 is therefore the systematic sweep's first previously-unfixed surviving defect.
  Fixed in SAS practical 6164, SHA d3b1b89822 (the tracked-mirror infrastructure was amended into the same commit).

F005 - KI#208 worst-enemy trade-memory recalculation flag overwritten - FIXED
  Classification: inherited Base AdvCiv bug
  Discovery route: second previously-unfixed defect found by the systematic newest-to-oldest historical sweep.
  Introduced in AdvCivPreSAS practical 2833, SHA 98b7a50fac:
    "Minor optimization in update of worst enemy"
  CvTeamAI::AI_updateWorstEnemy tried to avoid an unnecessary second worst-enemy pass by remembering whether trade/grant-memory decay had modified the tentative new worst enemy.
  The loop used bUpdateWorstEnemyAgain = (eOther == eBestTeam), so a later unrelated team with nonzero memory could overwrite an earlier true back to false. The needed recalculation therefore depended on team iteration order and could commit a stale m_eWorstEnemy.
  The fix makes the flag sticky: once eBestTeam is actually modified, later teams cannot clear the required recalculation.
  AdvCiv practical 2998, SHA 8c36049d43 ("Merge branch 0.99 into master"), carried the same branch change into master; no later historical correction was found and the assignment survived into current SAS.
  Fixed in SAS practical 6165, SHA 6b2c738295.

F006 - KI#209 random-leader reassignment state copied from random-civilization state - FIXED
  Classification: inherited Base AdvCiv bug
  Discovery route: third previously-unfixed defect found by the systematic newest-to-oldest historical sweep.
  Introduced in AdvCivPreSAS practical 2532, SHA 60a15e6434:
    "Handle assignment of random civs and leaders in the DLL"
  CvInitCore::reassignPlayer saved both bRandomCiv and bRandomLeader from m_abCivChosenRandomly, then later restored bRandomLeader into m_abLeaderChosenRandomly. A slot whose civilization and leader random-choice state differed therefore had its saved leader provenance forced to equal its civilization provenance.
  The distinction can matter when choices are independent, notably with GAMEOPTION_LEAD_ANY_CIV; wasLeaderRandomlyChosen and the later setup/re-randomization paths use the leader-specific flag.
  The fix changes the one incorrect read to m_abLeaderChosenRandomly.get(eNewID), preserving both flags independently without changing RNG or assignment policy.
  No later historical correction was found and the exact typo survived into current SAS.
  Fixed in SAS practical 6166, SHA eaf4c8ac19.

F007 - KI#210 vote-selection iterator refactor allowed voting-team self-contact - FIXED
  Classification: inherited Base AdvCiv bug
  Discovery route: fourth previously-unfixed defect found by the systematic newest-to-oldest historical sweep.
  Introduced in AdvCivPreSAS practical 2502, SHA cbc25c22bd:
    "Misc. refactoring"
  CvGame::doVoteSelection previously iterated unordered team pairs with iTeam2 = iTeam1 + 1. Practical 2502 replaced the inner numeric loop with a fresh full TeamIter but did not restore the self-exclusion, so a voting team could be paired with itself.
  Because isHasMet(self) starts false, the self-pair can call meet(self). CvTeam::makeHasMet checks eOther == getID() only after setting seen/met state, updating tech share and firing the Python firstContact event, so that late guard does not prevent the bogus self-contact state/event.
  The fix skips equal team IDs directly in doVoteSelection before attempting contact, restoring the lost caller invariant without changing generic meet semantics or foreign-team voting contact.
  No later historical correction was found and the iterator loop survived into current SAS.
  Fixed in SAS practical 6167, SHA 0e7098a6a6.

Resolved audit candidates
-------------------------
S001 - CvUnit::gift / AI_processPeacetimeGrantValue game-speed semantics - NO FIX
  Classification: currently safe under AdvCiv-SAS game-speed data; no SAS defect found.
  Unit gifts feed raw XML unit cost into a common peacetime trade/grant normalization path that divides by ResearchPercent.
  Every current SAS game speed uses the same TrainPercent and ResearchPercent (and also the same ConstructPercent and BuildPercent): 33, 50, 67, 100, 150, 200, 300 and 400 respectively across the eight speeds.
  Therefore the production-vs-research percentage distinction does not create game-speed drift in current SAS. Revisit only if those speed percentages are deliberately decoupled in the future.

S002 - CvPlayerAI::AI_espionageVal mixed production-cost semantics - NO FIX
  Classification: inherited K-Mod rough valuation design; mixed cost APIs alone do not establish a bug.
  KMod practical 161, SHA f9e8a3c4ce, deliberately increased project-destruction valuation while retaining getProductionNeeded(Project).
  KMod practical 960, SHA c4a6ecbc7a, deliberately rewrote destroy-building valuation around raw building cost plus production turns and AI_buildingValue.
  KMod practical 973, SHA 2bbcecb994, refined that formula again and explicitly described AI_espionageVal as a rough commerce-value heuristic; it also replaced the disabled buy-unit mission's relative AI_unitValue component with raw unit production cost.
  The current building formula's important time/utility term already contains production-turn scaling, while projects intentionally use their effective production cost and special strategic multipliers. The buy-unit espionage mission remains disabled.
  Conclusion: the formulas are heterogeneous by design and no current SAS correction is justified merely to make their cost APIs syntactically uniform. Revisit if espionage valuation itself is redesigned, not as an XMLCost bug.

F008 - KI#211 terrain attack sign reversal in unknown-defender AI strength estimates - FIXED
  Classification: inherited K-Mod/Base AdvCiv bug; exact pre-K-Mod authorship unknown.
  Discovery route: fifth previously-unfixed defect found by the systematic newest-to-oldest historical sweep, and the first surviving defect found after entering the K-Mod segment.
  Present in KMod practical 3, SHA 2414225e64 (initial source-bearing K-Mod snapshot, 27 Dec 2010).
  CvUnit::maxCombatStr has a special pAttacker == this mode for estimating an attacker against an unknown defender. City/hills/feature attack modifiers enter iTempModifier and are reversed at the end, but terrain attack was added directly to iModifier and therefore kept the wrong sign.
  Live AI_sumStrength/AI_currEffectiveStr callers reach this mode. GroupPathFinder uses the resulting strength in defended-plot attack-ratio/path costing, AI_cityTargetStrengthByPath uses it for reachable city attack strength, and current SAS low-power attacker ordering also calls the same effective-strength mode.
  Current SAS XML contains 30 unit types with nonzero terrain-attack modifiers. A simple +20% terrain attack case could be estimated as about 83.3% of base rather than the intended 120% before later effective-strength scaling.
  AdvCiv practical 1733, SHA 0d648df6db, touched/preserved the same asymmetric branch. No later historical correction was found before current SAS.
  Fix: change only the terrain branch accumulator from iModifier to iTempModifier. Known-defender semantics stay unchanged; unknown-defender mode now reverses terrain attack together with its sibling attack modifiers.
  Fixed in SAS practical 6168, SHA cf1272d7fe; user compile/run validation succeeded and CI passed. Practical 3 remains OPEN and the sweep must resume there before practical 2.


F009 - KI#212 AI-Barbarian CombatDetails attacker/defender field copy-paste - FIX PREPARED
  Classification: minor inherited K-Mod/Base AdvCiv semantic/API bug; exact pre-K-Mod authorship unknown.
  Discovery route: sixth previously-unfixed defect found by the systematic historical sweep, during the continuing deep audit of KMod practical 3.
  Present in KMod practical 3, SHA 2414225e64, and still present in current SAS.
  In CvUnit::maxCombatStr, the AI-controlled defender branch for a Barbarian attacker correctly applies the AI-Barbarian strength modifier but stores the reporting value in CombatDetails::iAIBarbarianCombatModifierTB (defender/"This is Barbarian") instead of the corresponding attacker field ...AB. The AB field is separately declared, zeroed, exported to Python and read by CvUtil.py, but was never assigned.
  Current built-in combat logging masks the defect because TB and AB use the same text key/sign handling, and combat strength itself is already computed correctly before the reporting assignment. The definite impact is therefore minor exposed-data/API semantics rather than combat odds or current AI behavior.
  Prepared fix: change only the one CombatDetails write from ...TB to ...AB. No strength arithmetic, RNG, handicap value, text key or balance data changes.
  Awaiting user compile/run/commit validation. Practical 3 remains OPEN and must resume before practical 2.

Recording rules
---------------
- Record clean progress as ranges rather than one line per harmless commit.
- For dense K-Mod/SAS archaeology, persist each completed checkpoint immediately instead of waiting for the whole segment or chat turn to finish. Use roughly 200 commits as a maximum checkpoint size and keep smaller live cursors while working when practical.
- Tooling/methodology note: this sweep was initially carried out primarily with ChatGPT in an interactive chat/tool environment (among other practical reasons, Codex usage availability was limited at the time). Interactive or otherwise non-persistent environments can sometimes interrupt a long review before a natural stopping point; more persistent coding-agent environments such as Codex or Claude Code may not share the same practical limitation.
- In an interactive/non-persistent environment, if a large commit or unresolved investigation is still in progress after roughly 20 minutes, save an OPEN checkpoint before continuing: preserve the last certified cursor, current candidate(s), partial findings/dispositions and exact next step. The ~20-minute interval is an empirical safety margin learned during this sweep, not a review-time limit or correctness rule; very large commits may span as many OPEN checkpoints as needed without advancing the certified cursor until the commit is genuinely closed.
- Never advance the certified cursor past an unfinished checkpoint merely because lower-numbered commits received exploratory spot checks.
- For every suspect/finding worth preserving, record segment, practical commit number, SHA, title, relevant file/function, classification and final disposition.
- Keep separate counts for open suspects, confirmed defects, actual fixes, inherited/pre-SAS bugs and SAS-specific regressions.
- A summary-only or partial archived diff is not automatically "clean"; if its title/path is relevant, inspect adjacent history/current source or obtain fuller source before closing it.
- Update Known Issues only for findings that deserve durable player/developer documentation; this tracker can hold weaker suspects and dead ends.
- Prefer accuracy over finding a bug in every commit. Most commits should be harmless.
